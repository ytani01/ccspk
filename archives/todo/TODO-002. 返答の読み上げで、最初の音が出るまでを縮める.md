## きっかけ

TODO-001 の作りでは、返答全体を合成し終えてから鳴らしていたので、128 文字で
最初の音まで約 11 秒かかった（`synthesis` 10.4 秒、音声 22.2 秒）。合成は再生の
約 2 倍の速さなので、文ごとに流せば待たずに済むと見た。

## やったこと

`hooks/speak-response.py` の合成と再生を、`sh -c`（`curl` 2 段 + 一時ファイル +
`pw-play`）から、同じスクリプトを `--play <本文>` で呼ぶ Python の子プロセスに替えた。

- 子の中では、スレッドが本文を「。！？!?」の後ろで文に分け、1 文ずつ urllib で
  合成してキューへ入れる。表側はキューから順に取り出して `pw-play -` の
  標準入力へ流す。一時ファイルも `curl` も要らなくなった
- 合成のスレッドは、どの例外で止まっても `finally` で終わりの印を入れる
  （reviewer の要修正。`IncompleteRead` などで子が止まったままになっていた）
- `audio_query` のタイムアウトを 5 秒から 60 秒にした。エンジンは要求を 1 つずつ
  処理し、hook が止めた前の返答の合成も最後まで続けるので、その後ろに並ぶと
  10 秒近く待つ（長い合成の最中に投げた `audio_query` が 9.9 秒待った、実測）。
  5 秒では黙って諦めていた
- 前の再生を止める前の判定を、cmdline に `--play` とスクリプト名があるかに替えた
- README の「返答の読み上げ」節を直した。TODO-006 の項目からも `curl` を外した

## 確かめたこと

同じ 128 文字・7 文で、hook の起動から `pw-play` が現れるまで。

| | 秒 |
|---|---|
| 直す前（main） | 10.95 / 10.80 / 10.44 |
| 直した後（main） | 1.48 / 1.95 / 3.94 |
| 直した後（verifier、タイムアウト 60 秒） | 2.18 / 3.91 / 3.98 / 2.34 / —（差し替え） / 1.48 |
| 直した後（main、main のターンの途中） | 1.47 / 1.65 / 2.83 / 3.66 / 3.82 / 3.67 |

- verifier の測定で 1 回ずつ「60 秒鳴らない」が出た。1 回目はタイムアウト 5 秒で
  黙って諦めたもので、60 秒にして直した。2 回目は、測っている間に main が
  利用者へ返事を終え、main の Stop hook が「新しい返答」として測定中の再生を
  止めたものと見ている。hook の仕様どおりの動き。main のターンの途中（main の
  Stop が起きない間）に 6 回測ると 6 回とも鳴った。`measure.py` には、
  測定中に PID ファイルが書き換わったら「差し替え」と出す判定を足した
- 文の継ぎ目の無音: 7 文を通しで鳴らして 0.01 秒（測定の刻み）。「はい。」の直後に
  句点の無い 82 字が続くと 1.28 秒（verifier）。README には「継ぎ目で数秒待つ
  ことがある」と書いた
- verifier: `--test` はコピーの区切りを「。」だけにすると AssertionError で落ちる。
  再生中の差し替えで前のグループは 0 個。本物の `claude -p` で cmdline に `--play` と
  本文が入る。エンジン停止中は終了コード 0 で、子は 2 秒後に 0 個。一時ファイルは
  増えない。長い合成でエンジンを忙しくさせても、9.05 秒で諦めずに鳴った
- reviewer: 要修正 1（上の `finally`）、検討 2。スレッドとキューをやめて 1 文先だけ
  合成する案は、継ぎ目の無音が今より出やすくなるので採らなかった。README の
  言い切り（「継ぎ目で待たない」「2 秒前後」）は弱めた

## 分担の振り返り

- **各担当が見つけたもの**: reviewer は、例外で子が止まったままになる経路を、
  仮のサーバーで実際に起こして見せた。コードを読むだけでは `except OSError` の
  外れに気づけなかった。verifier は「60 秒鳴らない」を 2 回拾った。原因の
  切り分けはさせていないので、main が引き取った。1 回目はタイムアウトの不具合、
  2 回目は測定のやり方の問題だった
- **見込みとの食い違い**: 担当の編成は見込みどおり。verifier を 2 回回したのは、
  1 回目の報告で見つかったタイムアウトを直したため
- **次に同じ規模なら**: 時間を測る確認は、main の Stop hook が動く環境では、
  main が返事を終えると測定が乱れる。verifier に測らせている間は main が
  ターンを終えないか、測定スクリプトに差し替えの判定を最初から入れておく。
  エンジンのような共有の資源に要求を投げる作りでは、「前の要求がまだ残って
  いる」状態での振る舞いを、最初の依頼の確認項目に入れる
