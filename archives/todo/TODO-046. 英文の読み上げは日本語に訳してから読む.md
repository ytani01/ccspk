## きっかけ

英文の返答は、日本語の話者が英語を読むので聞き取りにくい。あわせて、エンジンは文脈を見ずに読みを当てるので、
今日・辛い・行った・方のような単語を読み間違える（旧 TODO-047 をまとめた）。

立てたときの項目:

- [x] `ccspk translate on` で、整える前の返答のコードブロックの外にひらがな・カタカナ・漢字が 1 字も無ければ英文とみなし、子プロセスが
  `claude -p --model sonnet` で日本語に訳してから読む。`ccspk translate off` で訳さない。引数なしは今の状態を表示する。
  `~/.config/ccspk/translate` の有無で決め、次の読み上げから効く
- [x] 要約も入っていて長い英文なら、要約の 1 回で日本語にする（訳してから要約する 2 回にしない）
- [x] 訳に失敗したら、要約と同じく知らせずに元の英文を読む
- [x] `SUMMARY_PROMPT` と翻訳の指示に、文脈で読みが分かれる単語（今日・辛い・行った・方 など）はひらがなで書くよう足す
- [x] `demo()` に例を足し、`docs/UsersGuide.md`・`docs/Developer.md`・README.md に書く

背景（2026-09-29 に利用者と決めた）:

- 見分け方は「かなと漢字が無い」。日本語の文に英単語が混ざっているだけなら訳さない。英字の割合で決める案は、
  しきい値を決める手間があるので採らない
- 訳すのは要約と同じ `claude -p --model sonnet`（1 回に 1 セント前後、最初の音が 5 秒ほど遅れる）。Haiku にする案は、
  訳の質が落ちることがあるので採らない
- 料金がかかるので切り替えを付け、既定は切。`ccspk summary`・`ccspk queue`（TODO-045）と同じ形にする。環境変数での上書きは付けない
- TODO-045 と同じく `hook.py` の子プロセスを触るので、TODO-045 が済んでから着手する
- 旧 TODO-047（読みが分かれる単語をひらがなで書かせる）をまとめた（2026-09-29 に利用者と決めた）。どちらも
  `SUMMARY_PROMPT` を書き換え、verifier が本物の `claude -p` で確かめるので、1 回で済ませる
- 全文をひらがなにする案は採らない。エンジンは漢字かな混じりの文から単語の切れ目を推定してアクセントと区切りを
  決めるので、全部ひらがなにすると抑揚が平板になり、区切りもずれる。助詞の「は」「へ」も「わ」「え」と読ませられない。
  読みを決めるのに SudachiPy を使っても、エンジン（OpenJTalk）と同じ種類の推定なので、文脈で分かれる単語の精度は上がらない
- ひらがなの指示は、すでに `claude -p` を呼んでいる要約と翻訳に足すだけにする。追加の料金はかからない
- 要約も翻訳もしない短い文は今のまま。文脈を見ずに当てる辞書では直せないので、どれだけ読み間違えているかを
  点検の記録で見てから、別の項目で考える
- 着手後に決めたこと（2026-09-29、reviewer の指摘を受けて）: 要約・翻訳には整える前の返答を渡し、`claude -p` の出力を整える。
  英文の見分けも整える前の返答（コードブロックは除く）で行う。整えた後で見分けると、`tidy()` が足す「コード省略」「から」などで
  英文が日本語に見え、コードブロックや `TODO-NNN` を含む英文を訳さなかった
- 翻訳はイベントも字数も問わない（途中の文章や質問、短い英文も訳す）。料金がかかることは文書に書く（2026-09-29 に利用者と決めた）
- verifier には、読みが分かれる単語を含む返答を本物の `claude -p` で要約・翻訳させ、その単語がひらがなになるか、
  関係の無い漢字までひらがなにしていないかを確かめさせる

## やったこと

- `ccspk translate [on|off]` を足した（`~/.config/ccspk/translate` の有無。`switch()` を使い回す）
- `english()`: 整える前の返答から、コードブロック（新しい定数 `FENCE`。`tidy()` と共用）を除いて、ひらがな・カタカナ・漢字が
  1 字も無ければ英文とみなす
- `prepare()` は（整えた文、印、子プロセスに渡す本文）の 3 つを返す。印は `SUMMARIZE`・`TRANSLATING`・`None`。要約が先に効くので、
  長い英文は要約の 1 回だけ。書き直させるときの本文は整える前の返答で、翻訳はコードブロックの中身を空にしてから
  `TRANSLATE_MAX`（`LIMIT` の 3 倍、540 字）で切る。整えた文は空の判定と `LAST` との比べに使う
- `summarize()` を `rewrite(text, prompt)` に、`play_summary()` を `play_rewritten(text, flag, after)` にした。印から指示を引く
  `PROMPTS` を置いた。失敗・時間切れ・空なら `to_speech(本文)` を読む（知らせない）。中の `</reply>` は `unwrap()` で消す
- 指示: `TRANSLATE_PROMPT` を足し、`SUMMARY_PROMPT` の冒頭を「返答です（Markdown で書かれています）」に変えた。
  両方の終わりに `KANA_NOTE`（読みが分かれる単語を、意味に合う読みでひらがなだけで書かせる）を付けた
- `demo()` に、英文の見分け・振り分け・本文・`play_rewritten()` が印に合う指示を使うこと・`unwrap()`・失敗時の文を足した
- 文書: UsersGuide に 1.8 と 3.8 `ccspk translate` を足し（3.8 以降を 1 つずつ繰り下げた）、3.2・2.3 の表・3.6 を直した。

## 残ること

- 「行う」の活用形は漢字のまま残ることが多い（3 巡目で要約 3 回・翻訳 2 回）。送り仮名で読みが決まる形（行いました・行うか）は
  エンジンが「オコナイマシタ」「オコナウカ」と正しく読むので害は無い。「行って」はエンジンが「イッテ」と読むので、「テストを行って」の
  意味で漢字のまま残ると誤る（検証では出ていない）
- 翻訳で「コード省略」が抜けることがある（3 巡目で 3 回中 1 回）。コードを黙って飛ばすだけで、誤って読みはしない
- reviewer が挙げたが直していないもの: `main()` が子プロセスに本文を渡すところを `demo()` で確かめていない（`main()` はもともと通していない）、
  表や字下げしたコードに日本語がある英文は訳さない（境界線上）、要約に渡す量が増えた分の料金（文書に書いた）
- 要約も翻訳もしない短い文の読み間違いは今のまま（背景のとおり、別の項目で考える）

## 分担の振り返り

- reviewer は 1 回目で、整えた後の文で英文を見分けるとコードブロックを含む英文を訳さないことを実測で見つけた（仕様の字面どおりで
  main は気づかなかった）。2 回目で、その直しの結果、長いコードで説明が落ちることを見つけた。壊すと落ちるかの実測も 2 回とも効いた
- verifier は、プロンプトの例の書き方が出力に写ること（括弧で読みを添える、読みを 1 つに決めつける）を見つけた。静的なレビューでは捕まらない
- 見込みと食い違ったのは、reviewer 2 回・verifier 3 回になったこと。どれも、決めた前提（整えた文で見分ける、例 1 つで足りる）が
  外れたため。料金の 75% は main で、長い会話の読み直しが大きい
- 次に `claude -p` のプロンプトを変える項目では、実装の前に本物の `claude -p` で指示の文面だけを 2〜3 回試させる（verifier の手順 2 を
  先に回す）。reviewer への依頼では、仕様の字面と意図がずれそうな所（今回は「整えた文」）を名指しする
